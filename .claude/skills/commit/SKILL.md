# commit: 변경사항 분석 후 컨벤션 커밋

현재 git 저장소의 변경사항을 분석해 논리적 단위로 묶고, 각 단위에 맞는 한국어 커밋 메시지를 작성해 **사용자 승인 없이 바로 커밋**한다. 사용자가 이 스킬을 호출한 것 자체가 커밋 실행에 대한 사전 승인이다.

## 사전 확인

- 현재 디렉터리가 git 저장소인지 확인한다(`git rev-parse --is-inside-work-tree`). 아니면 사용자에게 알리고 종료한다.
- 저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 메시지 컨벤션이 별도로 정의돼 있으면, 이 스킬의 기본 형식(아래 3단계)보다 그 지침을 우선한다.

## 절차

### 1. 변경사항 분석 (git diff)

- `git status`로 추적되지 않은 파일까지 확인한다(대규모 저장소에서 메모리 이슈를 피하기 위해 `-uall`은 쓰지 않는다).
- `git diff`(unstaged)와 `git diff --staged`(이미 스테이징된 변경)를 모두 읽어 실제로 커밋 대상이 될 변경 전체를 파악한다.
- `git log --oneline -10`으로 최근 커밋 메시지 스타일(타입 prefix 사용 여부, 언어, 어미)을 확인해 기존 컨벤션과 일관성을 맞춘다.

### 2. 논리적 단위로 분류

- 변경된 파일을 목적 단위로 묶는다. 서로 무관한 변경(예: 디자인 수정과 스킬 추가)이 섞여 있으면 별도 커밋으로 분리할 것을 제안한다.
- 한 커밋의 "왜"가 한 문장으로 설명되지 않으면 분리 후보로 표시한다.
- 파일을 스테이징한 뒤에는 `git status`로 재확인해 의도치 않은 변경이 함께 포함되지 않았는지 점검한다.

### 3. 한국어 커밋 메시지 작성

- 형식: `<type>: <요약>`. type은 변경 성격에 맞춰 고른다.
  - `feat`: 새 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 빌드, 설정, 잡무성 변경
  - 그 외 저장소에 이미 쓰이는 타입(`docs`, `test`, `style` 등)이 있으면 그것도 허용한다.
- 요약은 "무엇을 왜" 바꿨는지 한국어 평서형 한 줄로 쓴다("~함", "~추가", "~수정" 등). 파일명 나열이나 "다양한 수정" 같은 모호한 요약은 쓰지 않는다.
- 여러 논리적 변경이 한 커밋에 불가피하게 섞였거나 배경 설명이 필요하면, 빈 줄 하나 띄우고 불릿으로 이유를 덧붙인다. 과도한 설명은 지양한다.
- 커밋 메시지에 시크릿·자격증명 문자열이 들어가지 않는지 diff를 다시 확인한다.

### 4. 승인 없이 바로 커밋

- 몇 개의 커밋으로 나눌지와 각 커밋의 메시지를 확정한 뒤, 되묻지 않고 곧바로 진행한다("이렇게 커밋할까요?" 같은 확인 질문을 하지 않는다).
- 커밋 단위별로 관련 파일만 명시적으로 스테이징한다(`git add -A`/`git add .`처럼 통째로 올리지 않는다).
- 커밋 메시지는 줄바꿈이 있을 수 있으므로 heredoc으로 전달한다.
- 현재 세션에 attribution 지침(예: `Co-Authored-By: ...`)이 있으면 커밋 메시지 끝에 포함한다. 없으면 생략한다.
- 커밋 후 `git status`와 `git log --oneline -n <커밋 수>`로 정상 반영을 확인하고, 실제로 만든 커밋 목록(해시·메시지)을 사용자에게 결과로 보고한다. 사용자가 명시적으로 요청하지 않는 한 push는 하지 않는다.
- **예외 — 이 경우에만 커밋을 멈추고 사용자에게 확인한다:**
  - diff에서 시크릿·자격증명으로 보이는 문자열을 발견한 경우
  - pre-commit 훅 실패가 반복되어 원인이 이 스킬 범위에서 고치기 애매한 경우
  - 커밋 대상 파일 중 사용자가 이 세션에서 만든 것이 아닌, 의도를 알 수 없는 미커밋 변경이 섞여 있는 경우

## 주의사항

- 이미 활성화된 git 안전 수칙(새 커밋 생성 원칙, `--no-verify`/`--no-gpg-sign` 금지, destructive 명령 금지, push는 별도 승인 필요 등)을 그대로 따른다. 이 스킬이 생략하는 것은 "커밋 자체에 대한 승인 질문"뿐이며, 그 외 안전 수칙은 동일하게 적용된다.
- pre-commit 훅이 실패하면 원인을 고치고 **새 커밋**으로 다시 시도한다(직전 커밋에 `--amend`하지 않는다 — 훅 실패 시 커밋 자체가 성립하지 않았으므로 amend 대상이 없다).
- 커밋할 변경이 없으면 빈 커밋을 만들지 않고 그 사실을 사용자에게 알린다.
